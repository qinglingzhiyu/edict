# 我用现代研发制度重新设计了 AI 多 Agent 协作架构

> 成熟的职场分工，比自由讨论的 AI 框架更懂效率。

## 一、一个奇怪的想法

去年底我开始重度使用 AI Agent 干活——写代码、做分析、生成文档。用的是市面上最火的几个多 Agent 框架。

用了一个月，我发现一个根本性的问题：

**这些框架没有“质量验收”这个概念。**

CrewAI 的模式是：几个 Agent 各自干活，做完就交。AutoGen 好一点，有个 Human-in-the-loop，但本质上是你自己当 QA。MetaGPT 有角色分工，但审核是可选的。

就像一家公司没有 QA 部门，工程师写完代码直接部署到线上。出了问题，你拿到最终结果时才知道翻车了，且无法复现，无法审计。

我一直在想：有没有一种架构，天然就把“审核”与“验收”嵌入到流程里，不是可选的插件，而是必须经过的关卡？

然后有一天，我对比了互联网大厂的研发流程——

**产品规划 -> 界面设计 -> 研发开发 -> 测试验收 -> 运维发布。**

任何一个功能，必须经过测试工程师的验收才能上线。这不就是我要找的架构吗？

## 二、大厂的架构智慧

这套研发制度不是花架子，它是一套经过数十年实践检验的分权制衡系统。

简化一下，信息流是这样的：

```
需求方（你）
  ↓ 提需求
PMO（立项）      ← 识别意图，建立项目
  ↓ 
产品经理（规划）  ← 编写 PRD，拆解子任务
  ↓ 
UI 设计师（设计） ← 输出高保真原型
  ↓ 
研发团队（执行）  ← 前端写页面，后端写接口
  ↓ 
测试工程师（验收） ← 质量把关，不行就打回修复
  ↓ 
运维工程师（发布） ← 生产环境部署上线
  ↓ 
汇报给 PMO 结项
```

注意这里最关键的一步：**测试工程师验收**。

研发开发完后，不是直接上线——必须先经过 QA 验收。QA 会检查：
- 功能是否符合 PRD？
- 界面是否还原了 UI 设计稿？
- 接口是否有安全风险？

如果不合格，QA 可以直接**打回 (Reject)**——让研发重新修复。这不是一个建议，是流程上的强制约束。

## 三、我把它做成了开源项目

我用 OpenClaw 搭了一个真正的 AI 研发中心。7 个 AI 岗位各司其职，严格按照权限矩阵通信。

项目叫 **Edict (Tech Dept)**，已开源：

**GitHub：https://github.com/cft0808/edict**

核心架构很简单：
- **PMO**：需求分拣、立项建档。
- **产品经理**：需求分析，输出 PRD。
- **UI 设计师**：输出 HTML/Tailwind 高保真原型。
- **研发团队**：前端/后端工程师，负责工程实现。
- **测试工程师**：编写用例，执行验收，Bug 反馈。
- **运维工程师**：CI/CD 部署，环境维护。

每个岗位有独立的 Workspace、独立的 Skills、独立的 LLM 模型。权限矩阵白纸黑字：研发不能跳过测试直接找运维，产品经理不能越权去改运维的配置。

## 四、研发看板——让一切可观测

光有架构不够，你还得看得见。

所以我做了一个**研发看板**——一个实时监控所有项目流转的 Web 面板。

10 个功能面板：
- **📋 需求看板**：任务卡片按 Backlog, Planning, Designing, Developing, Testing, Released 分列。
- **🔭 岗位调度**：可视化各岗位的负载、Token 消耗与健康卡片。
- **📜 项目归档**：展示完整的执行时间线，一键导出 Markdown 总结。
- **⚙️ 模型配置**：产品经理用 Claude 规划，后端用 GPT-4o 建模，测试用 DeepSeek 找 Bug——各取所长。

## 五、技术上的一些选择

做这个项目的时候，我做了几个刻意的技术决策：

**1. 流程化而非讨论化**
不是让 Agent 们在大群里自由讨论，而是通过状态机强制流转。

**2. 结果导向的 SOUL.md**
每个岗位的职责、输出规范都写在 Markdown 里。想提高测试标准？编辑 `agents/qa/SOUL.md` 即可。

**3. 权限矩阵是架构级的**
在配置文件里定义谁能调谁。这防止了 AI 协作中常见的“通信风暴”和“职责越权”。

---

## 六、最后

AI Agent 协作的核心问题不是“让 Agent 更聪明”，而是“让 Agent 的协作有规矩”。

CrewAI 解决了“多个 Agent 一起干活”的问题。
AutoGen 解决了“Agent 之间能对话”的问题。
**Edict 解决的是“AI 研发产出质量有保障”的问题。**

这可能是我见过的、最优雅的“AI 治理”方案。
